# 百工·墨（Mo）图像库选型

> 本文回答「图像编解码与像素处理用什么 Rust 库、色彩管理走多远」，对应
> [目标与里程碑.md](目标与里程碑.md) M0 的选型评审留档要求 · 2026-10-24。
> 文中版本号、发布日期、许可证、维护活跃度均于当日经 crates.io API 与
> GitHub 逐项查证（来源见文末）；性能不引外部数字，未实测的一律标「待验证」。

## 结论先行

- **主选 `image` crate 作为总入口**（格式探测、装载、保存），JPEG/PNG 的
  实际编解码由它内置的 `zune-jpeg`（解码）与 `png`（编解码）承担；
  `zune-jpeg`/`png` 同时保留为可直接引用的底层依赖（需要块级控制时直达）。
- **JPG**：解码走 `zune-jpeg`（image 0.25.0 起内置替换 jpeg-decoder），
  编码用 image 内置编码器（质量参数 1–100）；其 master 分支已改为包装
  `jpeg-encoder`（补上渐进式与色度抽样），随 image 下一版落地。
- **PNG**：编解码都走 `png` crate（image 内置 0.18.x），支持 8/16 位、
  iCCP 读写。
- **色彩管理**：M1 不做完整 ICC 变换，**只做 sRGB 假设 + ICC 元数据保全**
  （读出 ICC 挂在文档上、另存时写回）。完整色域变换等真实偏色需求出现
  再引入 `lcms2`（成熟，C 库绑定）；`moxcms`（纯 Rust，image 已内置依赖）
  作为观察对象。理由见「色彩管理」一节。

## 范围与前提

- 图像格式编解码**不经冶**（冶管音视频流），直接用 Rust 生态图像库——
  目标与里程碑.md 开发目标已定。
- 壳是 Tauri 2 + React；像素处理（图层合成、混合模式、调整、文字栅格化）
  全部在 Rust 侧内存中进行，前端只拿渲染结果。选型要同时满足 M1
  「打开/保存 JPG/PNG」和 M2+ 的像素管线。
- 内部工作格式定为 **RGBA8**（`image::RgbaImage`，即 `ImageBuffer<Rgba<u8>>`）：
  覆盖 JPG（无 alpha，装载时补不透明）与 PNG 8 位；16 位/浮点深度后置到
  M5+ 再评估（png 侧 16 位路径现成，image 也有 16 位变体，不构成阻塞）。

## 分项评审

### JPEG 解码：zune-jpeg（定案）

- image 0.25.0 起默认 JPEG 解码器就是 zune-jpeg（CHANGES.md「Switched to
  zune-jpeg for JPEG decoding」，0.25.9 又升到 0.5.x）——选 image 即已选中。
- 能力（其 README/文档自述）：baseline 与 progressive、SSE/AVX SIMD、
  严格安全（`unsafe` 仅限 SIMD 且可整体关闭）、**增量解码**（对截断流可
  输出稳定前缀/渐进预览）——大图打开体验的备用优化路径，M1 不用。
- ICC 读取可用：image 的 JPEG 解码包装层透传 `icc_profile()`
  （`src/codecs/jpeg/decoder.rs:126`），底层 zune-jpeg 解析 APP2 ICC 标记。
- `jpeg-decoder`（0.3.2）不再考虑：image 已弃它换 zune，社区维护重心
  转移，没有理由反向锁定旧栈。

### JPEG 编码：image 内置（近期升级为包装 jpeg-encoder）

- 当前发布版 0.25.10 的内置编码器：基线 JPEG、质量参数 1–100（默认 75），
  **无**渐进式、**无**色度抽样选择（查证自 v0.25.10 tag 的
  `src/codecs/jpeg/encoder.rs`，1228 行全在树内）。
- image master 已完成切换：`jpeg` feature = `zune-core + zune-jpeg +
  jpeg-encoder`（Cargo.toml:94，依赖 `jpeg-encoder 0.7` 带 `simd`），
  新增 `ChromaSubsampling`（4:4:4/4:2:2/4:2:0）枚举，质量 ≥90 默认 4:4:4。
  属「Version Next」未发布内容——**落地版本待验证**，M1 编码不依赖它。
- 若 M1 期间就需要渐进式导出（不该需要），可单独依赖 `jpeg-encoder`
  直编，接口稳定不因 image 版本节奏受制。

### PNG：png crate（定案）

- image 内置引用 png 0.18.x；纯 Rust、无 C 依赖，跨平台构建（含 Windows
  目标）省心。
- 能力对齐需求：8/16 位、调色板、Adam7 解码；编码侧 fdeflate 快速后端 +
  自适应滤波（0.18.1 还加了 MinEntropy 滤波与 Paeth 向量化优化）。
- iCCP **读**：`Info::icc_profile`（master `src/common.rs:728`，解码器
  另有 `set_ignore_iccp_chunk` 开关）；**写**：0.17.15 起提供 API
  （CHANGES.md「Add APIs to write ICC and EXIF chunks」），0.17.16 修过
  编码 bug，encoder 实现 `write_iccp_chunk`（master `src/encoder.rs:743`）。
- image 层同样透传：PNG 解码 `icc_profile()` 在 `src/codecs/png.rs:307`，
  写 ICC 于 image 0.25.6 进入（CHANGES.md「Implement writing ICC profiles
  for JPEG and PNG images」）。

### 为什么主入口选 image 而不是手工拼 zune-jpeg + png

- 一次 API 覆盖 M1 全部所需：格式探测、`DynamicImage` 装载、质量参数保存、
  像素格式转换；JPEG 与 PNG 路径恰好就是上面两个专项库，没有引入第二套
  实现。
- 已知问题（其 CHANGES.md 顶部自列）：解码器对恶意输入可能 panic（M1
  打开的是用户本地文件，风险可接受，后续可对装载加 catch_unwind 屏障）；
  「像素的色彩空间信息未清晰传递」——这正是色彩管理一节的出发点。
- 目标与里程碑.md 原则「优先成熟 Rust 生态（如 image 系），不自研」，
  image 2.25 亿下载、image-rs 组织维护，是该项原则的直接落地。

### 像素格式与性能特征

- 工作格式 RGBA8：与前端纹理传输（BGRA 互转）及 JPG/PNG 落盘路径最短；
  image 提供 `from_raw_bgra` 等转换构造（Version Next 新增，旧版手写
  通道交换），性能足够 M1/M2。
- 并行：image 默认 feature 含 rayon（解码与部分操作已并行）；M2+ 图层
  合成、M4 调整核可直接复用同一 rayon 池写并行像素循环。
- SIMD：zune-jpeg（SSE/AVX）与 png（fdeflate）自带；我们不写 SIMD。
- **性能数字一概未实测**：当前无业务代码，任何 MB/s 都是编造。M1 验收
  本身就是「打开→像素级查看→另存」真实往返，落地时以真实文件为准留档。

## 色彩管理

**决策：M1 只做 sRGB 假设 + ICC 元数据保全，不做完整 ICC 变换。**

理由：

1. M1 准入是「打开→查看→另存」往返，不是色彩还原评测；JPG/PNG 存量
   绝大多数是 sRGB，假设 sRGB 的显示结果对 M1 用户场景足够。
2. Rust 生态尚无即插即用的完整 ICC 管线：image 对色彩空间的支持刚起步
   ——0.25.7 通过 moxcms 加了 CICP 感知，官方说明「transforming 支持暂时
   有限、将逐步扩大」；moxcms 本身 2025 年才创建。完整能力现成的是
   `lcms2`（LittleCMS 绑定，成熟、MIT），但接入需要自建「读 ICC→建
   变换→逐像素转换」管线，M1 不值得。
3. image 自己在已知问题里写明「像素色彩空间未清晰传递」——在其之上强
   行做完整色彩管理，等于在流动的地基上盖楼。

但「保全」必须做，否则另存即丢色彩元数据：

- 打开时：经 `ImageDecoder::icc_profile()` 读出 ICC 字节（JPEG/PNG 均已
  透传），挂在文档模型上；非 sRGB 文件 M1 按原样像素显示（可能偏色），
  状态栏可提示「含非 sRGB 色彩配置」。
- 另存时：有 ICC 则写回——PNG 写 iCCP（png 0.17.15+），JPEG 写 APP2
  （image 0.25.6+），实现「打开→另存」元数据无损往返。

升级触发条件（写死，防「永远 sRGB」）：

- 真实用户文件出现广色域（Adobe RGB / Display P3）且偏色可感知 → 引入
  `lcms2` 做「输入 ICC→sRGB 编辑空间」变换，导出时可选择写回原 ICC 或
  转换目标色域；
- `moxcms`（纯 Rust、image 已带依赖）能力与 image 集成成熟后，优先评估
  替换 lcms2 的 C 绑定，减少原生依赖——**时间表待验证**。

## 决策汇总

| 事项 | 决策 |
| --- | --- |
| 总入口 | `image` 0.25.x（默认 feature，含 rayon） |
| JPG 解码 | image → zune-jpeg（内置） |
| JPG 编码 | image 内置编码器（质量参数）；渐进式/色度抽样等 image 新版或 `jpeg-encoder` 直用 |
| PNG 编解码 | image → png 0.18.x（内置） |
| 内部像素格式 | `RgbaImage`（RGBA8）；16 位/浮点后置 M5+ |
| 色彩管理 | M1：sRGB 假设 + ICC 读出/写回保全；完整变换触发条件如上，届时首选 `lcms2` |
| 弃用 | `jpeg-decoder`（image 已换 zune-jpeg，不再考虑） |

## 风险与待验证

- image「Version Next」的 JPEG 编码器切换（包装 jpeg-encoder）发布版本
  与时间待验证；M1 编码路径不依赖它，落地后跟进。
- 解码器对恶意输入可能 panic（image 自列已知问题）：M1 可先接受，装载
  入口加 `catch_unwind` 屏障是低成本兜底，实施与否待 M1 编码时定。
- ICC 写回在 image 层的 API 形态（0.25.6 进入，JPEG/PNG 均支持）需在
  M1 编码时实测确认行为符合预期——本文只验证了源码与变更记录存在。
- 性能（大图解码/编码耗时、图层合成帧预算）全部待 M1 起以真实往返实测
  留档，本文不含任何实测数字。
